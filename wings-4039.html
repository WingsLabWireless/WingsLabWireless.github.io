01 / Platform overview

Built for wireless experimentation

WINGS-4039 integrates a heavy-lift flight platform with a physically detachable, electrically independent experimental payload. The platform separates flight-critical functions from SDR research software and supports a bidirectional interface for communication-aware mobility.

Aircraft platform

Modular carbon-fiber/aluminum structure, high-current power distribution, CubePilot flight controller, and navigation sensors.

Experimental payload

Detachable rack for SDRs, computing hardware, RF front ends, antennas, and dedicated payload power management.

Mobility-aware experiments

Exchange UAV state and high-level position/heading requests while maintaining the distinction between research applications and flight control.

03 / Software and interfaces

Flight software meets SDR experimentation

The open-source software package is intended to document the interface between the UAV's flight-critical subsystems and experimental onboard computing—without making the SDR application responsible for stabilization or emergency behavior.

Aircraft-side software

  • Flight-controller configuration and tested firmware version
  • Vehicle calibration and navigation settings
  • State telemetry, logging, and diagnostic messages
  • Failsafe configuration and high-level command acceptance
  • Interface-controller firmware and protocol definitions
Firmware and configs: planned

Payload-side software

  • SDK / example client for UAV position and attitude
  • High-level position and heading request examples
  • SDR startup and data-logging templates
  • Timestamped synchronization of RF and vehicle state
  • Remote monitoring and experimental health reporting
SDK and examples: planned

Interface concept

Wireless application / SDR payload ⇄ Interface controller ⇄ Aircraft flight controller

High-level requests and telemetry cross the interface; flight stabilization and critical safety remain on the aircraft side.

Recommended protocol documentation

Publish a versioned message schema, field names and units, reference frames, transport/baud settings, command acknowledgments, heartbeat/timeout behavior, and rejected-command behavior. Include real example logs and minimal client examples when available.

Recommended version manifest

Record airframe revision, carrier PCB revision, flight-controller firmware version, interface-controller firmware commit, SDR model, OS/image, payload application commit, and dataset format version for each experiment.

04 / Assembly and reproducibility

Build, configure, and verify

A reproducible release should guide a new team from procurement through ground verification and supervised flight acceptance. The steps below are an outline—not a substitute for validated engineering drawings or a manufacturer-approved flight procedure.

1

Source components and fabricate parts

Use revision-controlled CAD, BOM, supplier references, fabrication tolerances, and part-inspection criteria.

2

Assemble the mechanical structure

Document arm geometry, load-bearing fasteners, propeller clearances, landing gear, center of gravity, and torque/inspection records.

3

Integrate electrical subsystems

Inspect polarity, connector ratings, wire routing, protective devices, grounding, and payload/aircraft power separation.

4

Install firmware and calibrate sensors

Record known-good configuration, IMU/compass calibration, positioning setup, and telemetry/failsafe validation.

5

Configure the modular SDR payload

Confirm mechanical retention, power limits, cooling, antennas, RF interconnects, and payload-specific mass balance.

6

Complete ground acceptance tests

Verify electrical stability, loss-of-link behavior, command limits, and logging before authorized flight operations.

7

Perform controlled flight qualification

Use approved test plans and incremental envelope expansion with an experienced team and emergency response arrangements.

8

Archive a reproducibility bundle

Preserve exact revisions, environmental context, setup photographs, test logs, configurations, and resulting datasets.

05 / Experimental methodology

Standardized testing approach

Testing should characterize both safe aircraft operation and the fidelity of wireless measurements. Publish methods, machine-readable logs, pass/fail criteria, and raw results so measurements can be reproduced—not merely headline performance claims.

A. Ground and electrical checks

Static power measurements, voltage stability, payload-rail behavior, fault isolation, telemetry operation, and EMI/RF baseline with propulsion inactive and active where safely feasible.

Protocol + logs: planned

B. Flight and load characterization

Flight stability, payload mass and balance, endurance, commanded motion, position/heading tracking error, and operating conditions.

Protocol + logs: planned

C. Wireless/RF characterization

Signal quality, throughput, packet delivery, interference baseline, antenna orientation, RF hardware configuration, and repeatability across flight trajectories.

Protocol + logs: planned

D. Communication-aware mobility

Compare commanded and measured position/heading, command latency, antenna pointing, link metrics, and rejection/failsafe behavior.

Protocol + logs: planned

E. End-to-end experiments

Integrated SDR/networking applications under realistic mobility, documented experiment scripts, and synchronized communications/flight logs.

Protocol + logs: planned

F. Data and reproducibility

Publish configuration manifests, clock references, vehicle pose, RF measurements, environmental metadata, processing scripts, and limitations.

Data schema: planned
Operational safety: Flight testing requires appropriate regulatory authorization, trained operators, a site-specific risk assessment, validated aircraft limits, and RF-spectrum compliance. No experimental payload software should bypass flight-critical safety checks.
