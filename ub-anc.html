UB-ANC Emulator

An Emulation Framework for Multi-Agent Drone Networks

Originally developed by Jalil Modares, Nicholas Mastronarde, and Karthik Dantu at the University at Buffalo.

Legacy research software

UB-ANC Emulator was originally developed during the 2015–2019 period. Its documented environment uses Ubuntu 16.04, QGroundControl 3.2, and ns-3.27. Running the project on a modern Linux distribution may require dependency updates, patches, or the original Docker environment.

Introduction

UB-ANC Emulator is an open-source software environment for designing, implementing, testing, and debugging missions involving one or more networked drones before moving to field experimentation.

It combines mission-planning logic, MAVLink-compatible flight control, software-in-the-loop simulation, sensing, data logging, ground-control visualization, wireless-network modeling, and optional integration with physical communication hardware.

The framework is designed to help researchers study communications, networking, robotics, autonomy, and multi-agent coordination as parts of one integrated cyber-physical system.

UB-ANC versus UB-ANC Emulator: UB-ANC is the physical airborne networking and communications testbed. UB-ANC Emulator is the software environment used to develop and test multi-drone mission logic before deploying it on the physical platform.
UB-ANC Drone in the Software-Defined Radio Configuration

The physical UB-ANC platform combines autonomous flight control, onboard computing, mission-control software, and a reconfigurable software-defined radio for airborne networking and communication experiments.

Key Features

Multi-Agent Emulation

Create multiple emulated drones, each with its own mission agent, flight-controller firmware, configuration, networking, and logging.

Real Flight Interfaces

Uses MAVLink and software-in-the-loop flight-controller firmware that closely match the interfaces used on physical drones.

Scalable Default Models

Lightweight flight and network models allow researchers to run larger multi-agent scenarios on conventional computers.

Realistic Networking

ns-3 integration supports protocol stacks, routing, wireless channels, interference, packet loss, throughput, and latency.

Ground-Control Tools

Emulated vehicles can be monitored through MAVLink-compatible ground-control applications such as APM Planner and QGroundControl.

Hardware Integration

Emulated agents may exchange traffic through physical radios, enabling software-defined radio and hardware-in-the-loop experiments.

Reusable Mission Logic

Mission-planning software can move from emulation to real hardware with minimal modification.

Structured Logging

Record vehicle position, flight state, MAVLink messages, network events, sensor measurements, and mission status.

How the Emulator Works

The following sequence summarizes the normal execution flow from startup to mission logging.

The Emulation Engine creates the scenario. It instantiates one MAV Object for every emulated drone.
Each MAV Object starts its internal components. These include the UB-ANC Agent, SITL flight controller, networking, sensing, MAVLink, and logging modules.
The Agent Control Unit executes mission logic. It determines the drone's actions based on mission state, local information, sensor inputs, and messages from other agents.
Flight commands are sent through MAVLink. The MAVLink Control Unit sends takeoff, waypoint, loiter, landing, and other commands to the SITL flight controller.
The flight-controller simulator updates vehicle state. Position, altitude, velocity, flight mode, and other state information are returned to the emulator.
Agents exchange network traffic. The Network Control Unit uses the default model, ns-3, a physical network interface, or software-defined radio hardware.
A ground-control station visualizes the mission. APM Planner or QGroundControl displays vehicle locations, status, paths, commands, and MAVLink messages.
Logs are collected for analysis. Mission, flight, sensing, and networking events can be stored for debugging, validation, and research analysis.

Physical UB-ANC Testbed

The physical UB-ANC platform combines an autonomous vehicle, an embedded computer, a MAVLink-compatible flight controller, and a configurable wireless communication subsystem.

Its modular architecture separates mission logic from the underlying network and flight-controller technologies. This makes it possible to evaluate the same application using Wi-Fi, Zigbee, LTE, GNU Radio, or software-defined radio hardware.

UB-ANC Testbed Software and Communication Architecture

The Agent Control Unit coordinates mission behavior through the Network Control Unit, MAVLink Control Unit, and Logging Unit. The communication interface can connect to GNU Radio and SDR hardware or to a conventional wireless network.

UB-ANC Emulator Architecture

The emulator is organized around three central elements: the Emulation Engine, one MAV Object for each vehicle, and the UB-ANC Agent that implements mission behavior.

UB-ANC Emulator Software Architecture

The Emulation Engine manages multiple MAV Objects. Each MAV Object contains the UB-ANC Agent, object attributes, network and sensor interfaces, logging, MAVLink control, and a software-in- the-loop flight-controller simulator.

UB-ANC Agent Model

Component Responsibility
Agent Control Unit (ACU) Contains mission-planning logic and determines the actions the drone performs.
Network Control Unit (NCU) Sends and receives information between agents, ground systems, network simulators, and external communication interfaces.
Sensor Control Unit (SCU) Supplies the mission logic with simulated or physical sensor measurements.
MAVLink Control Unit (MCU) Sends commands to and receives state information from a MAVLink-compatible flight controller.
Logging Unit (LU) Records vehicle state, mission events, MAVLink messages, network traffic, and sensing information.
SITL Simulator Runs the flight-controller firmware and vehicle dynamics without requiring physical flight-controller hardware.

Flight and Network Models

The default emulator prioritizes scalability. For network studies that require realistic packet-level behavior, UB-ANC can integrate with ns-3.

UB-ANC supplies agent behavior, mobility, and packet requests, while ns-3 models application, transport, network, link, physical, channel, mobility, and routing behavior.

ns-3 Integration with UB-ANC

Packet-transmission events, packet-delivery events, and vehicle position updates are exchanged between UB-ANC MAV Objects and their corresponding ns-3 nodes.

Network-Simulator Interface

Interface Purpose
netDataReady() Signals that a MAV Object has a packet ready for the network simulator.
netSendData() Delivers a packet from the network simulator to the destination MAV Object.
globalPositionChanged() Notifies the network simulator when an emulated drone changes position.

External Hardware Integration

UB-ANC supports progressive and mixed emulation. A researcher can emulate flight and mission behavior while routing communication through physical radio hardware.

USRP N210 Hardware-in-the-Loop Integration

Two emulated MAVs communicate through physical USRP N210 software-defined radios connected through an Ethernet switch, while their flight and mission behavior remain inside the emulator.

Software Prerequisites

The original installation instructions recommend Ubuntu 16.04. The documented emulator version uses QGroundControl 3.2 and ns-3.27. 

sudo apt-get update && sudo apt-get upgrade

sudo apt-get install build-essential \
    libgl1-mesa-dev \
    libsdl2-dev \

    libfontconfig1 \

    geoclue \
    curl \
    git \
    netcat \
    xvfb
Modern-system compatibility: This dependency list is historical. Some package names or versions may no longer be available on recent Linux releases. Use Docker or an Ubuntu 16.04-compatible virtual environment when possible.

Build

The project provides a build script that downloads, compiles, and configures the original emulator environment. 

cd ~

mkdir ub-anc
cd ub-anc

curl -sSL \
    https://raw.githubusercontent.com/jmodares/UB-ANC-Emulator/master/script/build_emulator.sh \
    | bash

After installation, the emulator should be available at: 

~/ub-anc/emulator/

Add the current user to the dialout group: 

sudo usermod -a -G dialout $USER
Important: Log out and log back in after modifying group membership.

Configuration: Objects Directory

The objects directory defines the emulated agents. Each subdirectory represents one vehicle and follows this format: 

mav_001
mav_002
mav_003
...
mav_250
File Purpose
agent Compiled mission executable for the corresponding drone.
arducopter Software-in-the-loop flight-controller firmware executable.
copter.parm Flight-controller parameter configuration.

To create ten agents using the default object template: 

cd ~/ub-anc/emulator

./setup_objects.sh 10

This creates mav_001 through mav_010.

Custom Missions

The default example uses the follower mission . New missions can be created from the UB-ANC Agent template .

  1. Implement the custom mission behavior.
  2. Compile the mission as an executable named agent.
  3. Copy it into the emulator's object template directory.
  4. Run setup_objects.sh to create the required number of agents.
  5. Start the emulator and monitor the mission.

Run the Emulator

cd ~/ub-anc/emulator

./start_emulator.sh

The startup script launches the flight-controller instances, establishes emulator connections, and then starts each mission agent.

Emulation and Experimental Validation

UB-ANC Emulator was evaluated by comparing software emulation with real drone experiments.

What Was Evaluated

  • A coordinated three-drone takeoff, loiter, communication, and landing mission.
  • Arming, landing, disarming, longitude, altitude, and mission timing.
  • Leader-follower scenarios with up to 100 emulated MAVs in the reported test environment.
  • Communication through physical USRP N210 radios.
  • Motor current, energy use, flight speed, and barometric pressure.
  • Link-level and end-to-end networking behavior using ns-3.

Research Applications

Energy-Efficient Coverage Path Planning

UB-ANC has been used to study coverage-path planning for single and multiple drones. The associated research models energy consumption based on traveled distance and turning behavior.

Planning methods were evaluated through optimization, emulation, and physical drone experiments with virtual obstacles.

Planned and experimentally executed coverage paths around virtual obstacles, comparing a depth-limited search method with the energy-aware LKH-D approach.

Limitations

  • The default flight model prioritizes scalability rather than full high-fidelity aerodynamic simulation.
  • The basic network model is range based. Realistic packet-level networking requires ns-3 or external communication hardware.
  • Timing differences can occur between emulation and physical flight, especially around takeoff and other flight transitions.
  • The original software dependencies are old and may not build directly on current Linux distributions.
  • The reported 100-agent scalability result was obtained using a specific historical computer and leader-follower scenario; it is not a universal maximum.
  • Successful emulation does not replace physical validation, flight safety reviews, trained operators, or compliance with applicable aviation regulations.

Advanced Options

QGroundControl, flight-controller, and ns-3 parameters can be passed or changed by editing the start_emulator function inside start_emulator.sh.

Console Mode

cd ~/ub-anc/emulator

./start_emulator.sh -c

The documented console-mode configuration uses AODV routing by default. Routing, propagation, gain, data rate, and logging settings can be adjusted in the startup script or associated ns-3 code.

Output Traces and Logging

The default startup script suppresses agent output by redirecting it to /dev/null. This reduces overhead when running many agents.

For debugging or experimental analysis, modify the startup script to display logs in real time or save them to files.

Scalability tip: Enable detailed console output only when necessary. Heavy logging can reduce emulator performance when many drones are active.

Docker

Docker provides the most practical way to reproduce the historical UB-ANC software environment.

Build the Image

docker build -t jmod/ub-anc-emulator:latest \
    https://raw.githubusercontent.com/jmodares/UB-ANC-Emulator/master/script/Dockerfile

Run with Linux GUI Support

xauth nlist $DISPLAY \
    | sed -e 's/^..../ffff/' \
    | xauth -f /tmp/.docker.xauth nmerge -

docker run -it \
    --env DISPLAY=$DISPLAY \
    --env XAUTHORITY=/tmp/.docker.xauth \
    --volume /tmp/.X11-unix:/tmp/.X11-unix \
    --volume /tmp/.docker.xauth:/tmp/.docker.xauth \
    --device /dev/dri:/dev/dri \
    --device /dev/snd:/dev/snd \
    --volume $PWD/docker:/tmp/emulator \
    --publish 5770:5770 \
    --publish 5780:5780 \
    jmod/ub-anc-emulator:latest

Run without GUI Mapping

docker run -it \
    --volume $PWD/docker:/tmp/emulator \
    --publish 5770:5770 \
    --publish 5780:5780 \
    jmod/ub-anc-emulator:latest

Inside the container: 

cp -r emulator/ /tmp/

cd /tmp/emulator
Historical container credentials: The original README lists both the username and password as ub-anc.

Port Mapping

Ground-control applications connect to agent i using: 

port = 10 * i + 5760
